## Структура підрозділів

### 3.1 Вибір мов та технологій програмування

- Обсяг за методичкою: 1–1,5 стор.
- База: `docs/sections/material-dlia-3.1-tekhnolohii.md` (джерела [10]–[22]).
- Підрозділи 3.1.1 / 3.1.2 з чернетки ВИДАЛИТИ — один суцільний підрозділ 3.1.
- Додати: рішення про відмову від ORM (сирий SQL через вбудований PostgreSQL-клієнт Bun) — методичка явно вимагає зазначити засоби доступу до даних.

### 3.2 Структурна схема (PSM)

- Нова діаграма, додаток **Н**.
- Уточнює додаток Г конкретними технологіями: React Router SPA (пакети з §2.5.2), шари Hono на Bun, WebSocket (hono/bun), better-auth + Google OAuth, Google Calendar API (Meet), поштовий сервіс Brevo, Bun.cron, PostgreSQL, локальне файлове сховище.
- У тексті: призначення кожного модуля + явне узгодження з діаграмою компонентів розділу 2 (методичка це перевіряє).

### 3.3 Реалізація компонентів серверної частини

Підрозділи нижчого рівня по реальних модулях, кожен з локальною діаграмою (блок-схема / діяльності):

- **3.3.1 Інтерактивна дошка**: WebSocket-кімнати по сесіях, типи повідомлень, відкладене (3 с) збереження стану в JSONB, PNG-знімок при завершенні.
- **3.3.2 Нагадування**: черга email_outbox, два cron-тики (формування — кожні 10 хв, надсилання — щохвилини), ідемпотентність через унікальний індекс.
- **3.3.3 Сесії та інтеграція з Google Calendar**: генерація посилань Meet, похідний статус сесії (SQL CASE) — невеликий фрагмент коду в додаток **Р** (лістинги).
- **3.3.4 Автентифікація та контроль доступу**: потік better-auth, ланцюжок проміжних обробників (сесія → заголовок ролі → guard-и → перевірка звʼязку психолог–клієнт).

### 3.4 Фізична модель БД

- Новий додаток **П**: фізична модель, побудована з реальних міграцій.
- Опис кожної таблиці (методичка вимагає «детальний опис кожної з таблиць»).
- Таблиці better-auth (user, session, account, verification) — керуються бібліотекою, показати спрощено.

### 3.5 Загальна діаграма класів

- Методичка вимагає діаграму класів, але код функціональний (заморожені const-обʼєкти `<Feature>Service` / `<Feature>Repo`, не класи).
- Рішення: моделювати ці обʼєкти як класи/інтерфейси з операціями для ключових доменів.
- ⚠️ Погодити з керівником.
