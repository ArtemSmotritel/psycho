3.1 Вибір мов та технологій програмування для реалізації сервісу підтримки віддаленої роботи психолога

(Примітка: цей підрозділ замінює чернеткові 3.1, 3.1.1 та 3.1.2 у робочому документі – підрозділи нижчого рівня 3.1.1 і 3.1.2 видаляються, текст нижче йде одним підрозділом.)

Для реалізації сервісу підтримки віддаленої роботи психолога використано набір сучасних відкритих технологій, які покривають серверну частину, клієнтську частину, збереження даних та інтеграцію із зовнішніми сервісами.

Мовою програмування для обох частин системи обрано TypeScript [10] – мову зі статичною типізацією, яка компілюється у JavaScript. Статична типізація дозволяє виявляти значну частину помилок ще до запуску програми, а оголошені типи слугують актуальною документацією коду: наприклад, види вкладень і ролі користувачів описані переліками літеральних типів, тому компілятор не дозволить пропустити обробку одного з варіантів або припуститися помилки у рядковому значенні. Крім того, інформація про типи забезпечує точні підказки редактора та безпечне перейменування при рефакторингу, що особливо цінно для проєкту, який розробляється й супроводжується однією людиною. Використання однієї мови для клієнтської та серверної частин зменшує перемикання контексту під час розробки, хоча кожна частина має власні, незалежні моделі даних.

Середовищем виконання серверного коду обрано Bun [11] – сучасне середовище виконання JavaScript і TypeScript. Bun вирізняється високою швидкістю роботи та містить вбудовані інструменти: менеджер пакетів, виконавець тестів, клієнт для PostgreSQL та підтримку WebSocket-з'єднань. Це зменшує кількість зовнішніх залежностей проєкту. Зокрема, вбудованим виконавцем тестів Bun виконуються всі інтеграційні тести серверної частини, тож окремий тестовий фреймворк встановлювати не довелося.

Для побудови серверного REST API використано легкий вебфреймворк Hono [12]. Він надає маршрутизацію запитів, механізм проміжних обробників (middleware) для наскрізних задач, таких як перевірка прав доступу, та безпосередньо підтримує середовище виконання Bun.

Для зберігання даних обрано PostgreSQL [13] – відкриту обʼєктно-реляційну систему керування базами даних. Це зріла СКБД, перевірена десятиліттями промислової експлуатації, з докладною документацією та безкоштовною ліцензією, що важливо для проєкту без бюджету на ліцензування. Її багатий діалект SQL – часткові індекси, індекси за виразами, тригери – дозволяє переносити частину логіки на рівень бази даних: у проєкті саме на них спираються ідемпотентна черга листів-нагадувань та автоматичне створення профілів ролей при реєстрації користувача. Нарешті, PostgreSQL має розвинені засоби роботи з датами й часом: тип даних з урахуванням часового поясу зберігає саме момент часу, а не локальний запис, що критично для планування сесій, коли психолог і клієнт можуть перебувати у різних часових поясах.

Для організації доступу до даних свідомо не використано ORM-бібліотек: усі запити виконуються як параметризовані SQL-запити через вбудований PostgreSQL-клієнт середовища Bun [11]. Такий підхід дає повний контроль над текстом запитів, зокрема дозволяє обчислювати похідні значення (наприклад, поточний стан сесії) безпосередньо у запиті, спрощує оптимізацію та не додає до проєкту зайвої залежності; параметризація запитів при цьому захищає від SQL-інʼєкцій. Зміни схеми бази даних виконуються послідовністю SQL-міграцій, які зберігаються у репозиторії проєкту та застосовуються власним сценарієм міграцій.

Клієнтська частина побудована на бібліотеці React [14], яка реалізує компонентний підхід до побудови інтерфейсів користувача та декларативне оновлення відображення при зміні даних. Для організації маршрутизації односторінкового застосунку (SPA) використано фреймворк React Router [15], який відповідає за структуру сторінок, завантаження даних та навігацію без перезавантаження сторінки.

Для стилізації інтерфейсу використано Tailwind CSS [16] – CSS-фреймворк утилітарних класів, що пришвидшує верстку та забезпечує єдиний візуальний стиль, а також бібліотеку компонентів shadcn/ui [17], яка надає готові доступні елементи інтерфейсу (форми, діалоги, меню) з можливістю повної адаптації під потреби проєкту.

Для автентифікації користувачів використано бібліотеку Better Auth [18] у поєднанні з протоколом OAuth 2.0 від Google [19]. Такий підхід дозволяє користувачам входити в систему через наявний обліковий запис Google, а сама система не зберігає паролів, що зменшує ризики, повʼязані з витоком облікових даних.

Взаємодія у реальному часі, необхідна для спільної роботи на інтерактивній дошці, реалізована на основі протоколу WebSocket [20], який встановлює постійне двонаправлене зʼєднання між браузером і сервером та дозволяє обом сторонам надсилати повідомлення без повторних HTTP-запитів. Канва малювання побудована на відкритій бібліотеці Excalidraw [21], що надає готові інструменти малювання від руки, геометричні фігури, текст та роботу із зображеннями.

Інтеграція із зовнішніми сервісами Google реалізована через Google Calendar API [22], який дозволяє програмно створювати події календаря з автоматично згенерованими посиланнями на відеозустрічі Google Meet, що закриває потребу у відеозвʼязку без розробки власного рішення. Для надсилання електронних листів (запрошення клієнтів та нагадування про сесії й рекомендації) використано сервіс транзакційної пошти Brevo [23] через його офіційну бібліотеку: він бере на себе доставку листів і не потребує розгортання власного поштового сервера.

Середовищем розробки обрано редактор коду Zed [24] – швидкий редактор із вбудованою підтримкою протоколу мовних серверів (LSP), завдяки якій перевірка типів TypeScript, автодоповнення та навігація кодом працюють однаково для клієнтської та серверної частин проєкту.

Усі обрані технології є відкритими або безкоштовними для використання, мають активні спільноти та докладну документацію.
