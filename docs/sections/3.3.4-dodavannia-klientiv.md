3.3.4 Реалізація додавання клієнтів

(Примітка: блок-схеми винесено в окремі додатки. Літери додатків слід узгодити з фінальним порядком додатків; у тексті нижче вони позначені умовно як «додаток Х» та «додаток Y». Номер підрозділу узгодити з фінальною структурою розділу.)

Пакети «Створення запрошень» та «Керування клієнтами» встановлюють зв'язок «психолог–клієнт». Їх проєктування описано в підрозділі 2.6.Х. Реалізація має два шляхи: прямий зв'язок із зареєстрованим клієнтом та запрошення для незареєстрованого. Кожен шлях виконує окремий метод сервісу.

Прямий зв'язок виконує метод linkByEmailToPsycho(psychoId, email) класу ClientsService. Метод шукає клієнта за поштою. Якщо облікового запису немає, він видає помилку ClientNotFound. Якщо пошта належить самому психологу, він видає SelfLinkNotAllowed. Якщо зв'язок уже існує, він видає AlreadyLinked. Інакше метод створює зв'язок через ClientsRepo.linkClientToPsycho().

Блок-схема створення запрошення наведена в додатку Х. Її виконує метод createForPsycho(psychoId, email) класу InvitationsService. Метод приводить пошту до нижнього регістру і прибирає пробіли. Далі він шукає користувача з такою поштою. Якщо це сам психолог, метод видає SelfLinkNotAllowed. Якщо користувач існує і вже пов'язаний із психологом, метод видає AlreadyLinked. На блок-схемі ці дві перевірки об'єднані в один ромб, а відмови показано без кодів помилок.

Далі метод шукає відкладене запрошення для цієї пари «психолог — пошта». Якщо воно є, метод повертає його без змін. Тому повторний запит не створює дубля. Якщо запрошення немає, метод відкриває транзакцію db.begin. У ній він вставляє запис у таблицю invitations і ставить лист у чергу email_outbox викликом enqueueInvitationCreated(). Обидві дії виконуються разом. Запрошення не існує без листа, а лист не існує без запрошення. Сам лист надсилає тік відправника, описаний у підрозділі 3.3.3. Тому недоступність поштового сервісу не блокує створення запрошення. Метод повертає запрошення з полем inviteLink. Функція buildInviteLink(token) будує посилання з токеном на основі адреси фронтенду. Запрошення не має терміну дії.

Блок-схема прийняття запрошення наведена в додатку Y. Її виконує метод acceptByToken(token, userEmail, userId). Клієнт має увійти через Google, перш ніж надіслати токен. Метод виконує п'ять перевірок у такому порядку. На блок-схемі перевірки 1 і 2 об'єднані в один ромб, так само 4 і 5. Перевірка 3 має власний ромб. Відмови показано без кодів помилок:

1. Запрошення з таким токеном існує. Інакше метод видає NotFoundError.

2. Запрошення ще не прийняте. Інакше метод видає AlreadyAccepted.

3. Пошта облікового запису збігається з поштою запрошення. Інакше метод видає EmailMismatch. Ця перевірка не дає прийняти запрошення чужим токеном.

4. Користувач не є психологом, який створив запрошення. Інакше метод видає SelfLinkNotAllowed.

5. Користувач ще не пов'язаний із цим психологом. Інакше метод видає AlreadyLinked.

Якщо всі перевірки пройдено, метод відкриває транзакцію. У ній markAccepted() змінює статус запрошення на «accepted», а ClientsService.linkClientToPsycho() створює зв'язок. Запрошення не стає прийнятим без зв'язку. Метод повертає ідентифікатори психолога і клієнта.

Маршрути лише викликають ці методи. Маршрут створення запрошення доступний тільки психологу. Маршрут прийняття доступний будь-якому користувачу з сесією. Маршрут видалення запрошення викликає метод deleteForPsycho(), який видаляє лише відкладені запрошення цього психолога.
