3.2 Структурна схема реалізації сервісу підтримки віддаленої роботи психолога

(Примітка: структурну схему винесено в окремий додаток. Літеру додатка слід узгодити з фінальним порядком додатків; у тексті нижче він позначений умовно як «додаток И».)

У додатку И наведено структурну схему реалізації сервісу підтримки віддаленої роботи психолога. Вона є платформозалежною моделлю (PSM): деталізує уточнену діаграму компонентів (додаток Г) обраними у підрозділі 3.1 технологіями та відображає розподіл програмного забезпечення за вузлами розгортання. На відміну від діаграми компонентів, яка є платформонезалежною (PIM), структурна схема вказує, у якому середовищі виконується кожна підсистема, якими протоколами й драйверами реалізовано звʼязки між ними та які обмеження накладає спосіб розгортання. Склад сервісів і напрямки звернень при цьому збережено з діаграми компонентів.

Клієнтську частину розгорнуто у вузлі «Браузер користувача» — односторінковому застосунку (SPA) на TypeScript, бібліотеці React та фреймворку React Router. Усередині виділено компоненти: автентифікації та вибору ролі (Better Auth); два рольові інтерфейси — «Інтерфейс психолога» та «Інтерфейс клієнта» (shadcn/ui, Tailwind CSS); інтерактивну дошку (Excalidraw); та API-клієнт (Axios), через який проходять усі вихідні запити до сервера. Актор «Психолог» працює з компонентом автентифікації та інтерфейсом психолога, актор «Клієнт» — з компонентом автентифікації та інтерфейсом клієнта. Обидва рольові інтерфейси використовують спільну дошку і звертаються до сервера через спільний API-клієнт.

Серверну частину розгорнуто в межах одного процесу середовища виконання Bun (стереотип «singleInstance»), який поєднує HTTP API, шлюз WebSocket-зʼєднань та внутрішньопроцесний планувальник; серверний код написано на TypeScript із фреймворком Hono. Всередині процесу виділено такі компоненти: «HTTP API» (Hono з проміжними обробниками сесії та контролю ролей) — єдина точка входу REST-запитів; «Whiteboard WebSocket-шлюз» (createBunWebSocket) — обмін станом дошки у реальному часі; «Scheduler» (Bun.cron) — запуск обробки черги листів за розкладом; «Notification Service» — черга листів-нагадувань і запрошень; «Better Auth» — автентифікація та перевірка ролей. Доменну логіку реалізовано сервісами Users Service, Client Service, Invitation Service, Session Service, Whiteboard Service, Session Attachment Service, File Storage Service, Associative Image Service, Dashboard Service та Progress Service. Доступ до даних усі сервіси отримують через окремий шар репозиторіїв, що інкапсулює SQL-запити.

Звʼязки всередині процесу відтворюють маршрутизацію звернень. «HTTP API» маршрутизує запити до компонента автентифікації та доменних сервісів. «Whiteboard WebSocket-шлюз» звертається до компонента автентифікації для перевірки доступу, до Session Service — для перевірки прав на сесію, до Whiteboard Service — для збереження й віддавання стану дошки. Session Attachment Service та Associative Image Service користуються File Storage Service для роботи з файлами; Session Service делегує Whiteboard Service очищення дошки при завершенні сесії. Такти опрацювання черги надходять до Notification Service від планувальника, а також від Invitation Service та Session Attachment Service, які не надсилають листи самостійно, а ставлять їх у спільну чергу.

Збереження даних забезпечує окремий екземпляр PostgreSQL (стереотип «subsystem») зі схемою даних: користувачі, сесії, вкладення, асоціативні зображення, метадані файлів та сповіщення. Доменні сервіси працюють з даними лише через шар репозиторіїв, який виконує параметризовані SQL-запити через вбудований у Bun PostgreSQL-клієнт (інтерфейс «Bun SQL»). Окремим каналом до тієї ж бази звертається Better Auth — через власний драйвер node-postgres (пул pg Pool, інтерфейс «node-postgres»), тому на схемі цей звʼязок показано окремо від репозиторіїв застосунку.

Завантажені файли зберігаються у файловому сховищі на локальному диску хоста застосунку; звертається до нього лише File Storage Service, решта сервісів працюють з файлами через його інтерфейс. Взаємодію із зовнішніми сервісами показано трьома каналами: Better Auth — до Google OAuth 2.0 (OAuth 2.0 поверх HTTPS) для входу через обліковий запис Google; Session Service — до Google Calendar API (REST поверх HTTPS, googleapis) для створення подій із посиланнями на відеозустрічі; Notification Service — до сервісу транзакційної пошти Brevo (REST поверх HTTPS) для доставки листів.

Стереотип «singleInstance» і примітка до нього фіксують обмеження реалізації: систему розгортають в один екземпляр. Внутрішньопроцесний планувальник і локальне файлове сховище не поділяються між репліками, тому запуск кількох копій процесу без винесення планувальника й сховища в зовнішні служби спричинив би дублювання листів і неузгодженість файлів. Для передбачуваного навантаження одноекземплярне розгортання є достатнім і спрощує експлуатацію.

Отже, структурна схема поглиблює діаграму компонентів розділу 2, залишаючись узгодженою з нею. Порівняно з нею на схемі ідентифіковано технології реалізації кожної підсистеми, деталізовано протоколи та драйвери звʼязків (REST/HTTP, WebSocket, Bun SQL, node-postgres, OAuth 2.0, REST/HTTPS), показано вузли розгортання та явно зафіксовано обмеження одноекземплярного розгортання. Це дає конкретне уявлення про реалізацію системи та середовище її виконання й слугує основою для опису реалізації окремих компонентів у наступних підрозділах.
